# System audit — 31 Aug 2026

Is the system functional, is it structurally sound, and does it match the
documentation? Audited against `CaterSync Main.pdf` §4.1.1 and the live tree.

Method: three independent passes (correctness, build integrity, documentation
conformance), then **every finding re-verified by hand against the live files**
before it was written down here. That last step mattered more than expected —
see §0.

---

## 0. Three "critical" findings were false alarms, and that is worth knowing

Two of the three passes opened with the same show-stopper: **the build is
broken**, `utils/vehicle.js` exports only one symbol while five pages import six
others, and `Reports/helpers.js` is missing `cardAccentClass`. A third pass
independently reported the date-range inversion guard as entirely absent.

All three are wrong, and the cause was mine. The working copies they read were
**stale** — the file-transfer layer returned cached versions rather than what is
on disk. Checked against the live files:

| Alleged defect | Reality |
|---|---|
| `utils/vehicle.js` exports only `getDailyVehicleSnapshot` | The live file is **1,141 lines** and exports **37 symbols**, including all six named as missing |
| `Reports/helpers.js` has no `cardAccentClass` | Present, `helpers.js:111` |
| Date-range inversion guard missing at all three layers | All three present: `DateRangeFilter.jsx:64` (`min={customStart}`), `:17` (carry-along), `helpers.js:60-72` (the swap) |
| Vehicles delete asks for the password before checking | Fixed. Checks at `:606` and `:615` run before the confirm at `:620` |

**The build is fine.** Nothing below is a build break.

This is the same failure mode `HANDOFF.md` already warns about — *"A working copy
staged earlier in a session can be several commits behind"* — arriving from a new
direction. Everything reported from here on was read from the live file.

---

## 1. Verdict

**The web app is functional and structurally sound.** It is also, in most
respects, **ahead of its own documentation** — several requirements the document
marks as unmet are in fact built, just built elsewhere or better than described.

Three things are genuinely wrong and one of them is corrupting money data. The
larger risk to the grade is not the code: it is that the panel will mark the
system against a schema table and a requirements list that no longer describe it.

| | Count |
|---|---|
| Confirmed defects that produce a wrong answer or corrupt data | **6** |
| Documented requirements the code contradicts | **3** |
| Documented schema items that no longer match reality | **~30** |
| Requirements met but described wrongly in the document | **4** |

## 2. Confirmed defects, most severe first

### D1 · "Mark as Completed" promotes unverified and rejected payments to Fully Paid
`Bookings.jsx:1063-1066`, `ShortOrders.jsx:1010-1013` — **verified by hand**

The shared hook narrows the update correctly:

```js
// useCompletionHandlers.js:82-85
.update({ pay_status: 'Fully Paid' })
.eq('booking_id', booking.booking_id)
.eq('pay_status', 'Downpayment')     // ← narrowing
.gt('amount_paid', 0);               // ← narrowing
```

Both list pages kept a private copy that never got the fix:

```js
// Bookings.jsx:1065-1066
.update({ pay_status: 'Fully Paid' })
.eq('booking_id', id);               // ← every payment row
```

The hook's own comment documents this exact bug as fixed. It was fixed in the
hook and in neither copy.

**What happens:** a customer uploads a duplicate ₱20,000 proof by mistake; it
sits as `Pending Verification`. The manager completes the booking **from the
Bookings list**. That row silently becomes `Fully Paid`, so `isUnverifiedPayment`
stops excluding it and it counts as collected money on the Dashboard, the
Payments cards and the Financial tab. A proof a manager explicitly **rejected**
is promoted the same way. Complete the same booking from its **detail page** and
none of this happens — two buttons with one label and different results.

### D2 · Approval charges the full package price per extra guest on fixed-price packages
`useApprovalHandlers.js:108-110` — **verified by hand**

```js
const pkgPrice = approvalBooking?.package?.pkg_price || 0;
const extraPaxCost = (updated.extraPax || 0) * pkgPrice;
```

No `pricing_type` branch. Every other place that prices extra guests branches
correctly — the create form at `Bookings.jsx:122-132` uses `extra_pax_price` when
`pricing_type` is fixed.

**What happens:** a ₱25,000 fixed package for 50 guests with `extra_pax_price`
₱400. At approval the manager adds 5 extra guests. The modal reads **New Total
₱150,000** instead of ₱27,000, and writes it. The required downpayment, the
outstanding balance, the contract value and every report inherit a ₱123,000
error. This is the single most expensive wrong number in the system.

### D3 · Editing any booking shifts its event by the UTC offset
`Bookings.jsx:594`, `BookingDetails.jsx:604`, `ShortOrders.jsx:582`,
`ShortOrderDetails.jsx:552` — **verified by hand**

All four load the field as `new Date(event_datetime).toISOString().slice(0, 16)`
— a **UTC** wall clock — into a `datetime-local` input, which means local. Saving
re-parses it as local.

**What happens (PHT, UTC+8):** an event at 18:00 opens in the editor showing
**10:00**. The manager fixes a typo in the venue and saves without touching the
date; the event moves eight hours earlier. A 06:00 morning event moves to the
**previous day** on the first save, dropping out of every same-day availability
check. `Dashboard.jsx:20-25` documents this exact trap — these four forms are the
ones that still do it.

### D4 · "Total Collections" is gross under a caption promising net
`Payments.jsx:272-273`, `:1130` — **verified by hand**

`typeAndDateFiltered` drops every negative-amount row on the Payments tab, and
the card is computed from that filtered set — then captioned **"Already
subtracts any refunds"**. `getPaymentsReceived` is net only *because* refunds
arrive as negative rows, and they have been removed before it sees them.

Take ₱300,000 and refund ₱40,000: the card reads ₱300,000 and claims the refund
is already deducted. Dashboard and Reports compute it from unfiltered rows and
are correct, so the three screens disagree — the precise defect
`reportMetrics.js` was written to end.

### D5 · A failed stock check is treated as a passed one
`Equipment.jsx:694-696` and `:782-784` — **verified by hand**

```js
} catch (checkError) {
  console.warn('Committed-quantity check failed:', checkError);
}
// ...falls straight through to the update
```

The equivalent guard on the assign path aborts correctly. Here, if the impact
query fails on a transient network error, the warning goes to the console and
the stock reduction is written anyway. 50 chairs, an event next week needs 45,
the manager flags 40 damaged — the guard that should stop it silently doesn't,
and the shortage surfaces next week.

### D6 · The Menu Item Mix footer prints a reconciliation that doesn't reconcile
`Reports/index.jsx:393-396` — **verified by hand**

```js
if (selections.length === 0) return;   // ← line 393
const deliveryFee = b.delivery_fee || 0;
deliveryFeeTotal += deliveryFee;       // ← line 396, never reached
```

A short order whose `menu_selections` is null or unparseable contributes to
neither menu revenue nor delivery fees — but its `total_amount` is still in
`shortOrderRevenue`. The footer prints "Menu items + Delivery fees" over a rule
line, then a Short order revenue total that is larger than their sum, with the
difference unexplained.

## 3. Where the code and the documentation contradict each other

### C1 · SFR-MA-05 says same-date blocking. The code deliberately allows same-date reuse.
**Fix the document.**

> "The system shall automatically prevent the manager from assigning vehicles or
> equipment that are already booked for another event **on the same date**."

The vehicle half of that is no longer true, on purpose. `utils/vehicle.js` now
blocks only when two **trip windows overlap**, so one van can set up a morning
wedding and deliver in the afternoon.

That change came from Vaughn describing what PG's actually does. And the
document argues against itself here: §1.1 says the business runs several
bookings a day, while SFR-MA-05 as written caps it at one event per vehicle per
day. **The code is right and the requirement is wrong.** Rewrite it as a
trip-window rule; `blueprint-03-dispatch.md` §4.2 has the wording.

### C2 · There is no role-based access control. NFR-05 and SFR-03 claim there is.
**Fix the document.**

> NFR-05: "...enforce role-based access control..."
> SFR-03: "The system shall allow users to restrict access to features and data
> based on user type."

An exhaustive search for `role`, `user_type`, `permission`, `is_admin` returns
**nothing** outside JSX attributes. The entire authorisation model is
`ProtectedRoute.jsx:17` — `if (!user || !isManager) → /login` — where `isManager`
is one existence check against the `manager` table. Every authenticated manager
sees every route.

The four user types are separated by **being four different applications sharing
one Supabase project**, which is app-level separation, not RBAC, and is only as
strong as the Supabase RLS policies (not in this repo, not verifiable here).

**The same requirement's other half is met, and better than documented.**
Passwords are bcrypt-hashed in Supabase Auth; the app never reads a `password`
column. But Table 4.2.3.3.1 still shows `CUSTOMER.password` and
`MANAGER.password` holding `customerpass!123` and `managerpass!123` in plain
text. **If the panel asks where passwords are stored, your own document gives
the worst possible answer to a question the system actually answers well.** Fix
that table before the defense.

### C3 · The ethics commitment to an audit trail is not implemented.
**Fix the code.**

§3.6 promises: *"Any activities performed in the system, including bookings
approved, vehicles assigned, payments made... will be recorded... a record of who
has done what and when."*

Nothing records **who**. Verified: booking approval writes no actor; the payment
insert has no `manager_id`; the `vehicle_assign` insert has no `manager_id` —
**even though `manager_id` is in the documented schema for that table.**
`manager_id` is read in exactly two places and used only for the single-session
lock. "When" partly exists (`pay_datetime`, `assigned_at`, `returned_at`); "who"
exists nowhere.

The cheapest fix in this entire report: populating `vehicle_assign.manager_id` on
insert is one line, closes a documented column, and partly honours an ethics
commitment. Do that one regardless.

### C4 · Four requirements are met but described wrongly
**Fix the document** — these are free marks currently being lost.

| Requirement | Reality |
|---|---|
| UFR-MA-02 "event calendar module" | A real month-grid calendar **exists** — `Dashboard.jsx:405-427`, rendered `:815-880`, with month navigation, type-coded day dots, a legend and day-click drill-through. But there is no `/app/calendar` route and no nav item, so the promised *module* doesn't exist as one. Either reword to "a calendar view on the Dashboard", or lift the existing component to its own route — that is a small change that makes the document true. Don't claim "manage": it is read-only. |
| NFR-05 credential encryption | Met via Supabase Auth, contradicted by your own schema table (C2) |
| UFR-MA-08 "add-on services" | Packages, menu items and prices have full CRUD. **No add-on-services entity exists** — no table, no column, no UI. Drop the phrase or define it as booking-level adjustments. |
| SFR-CU-07 "automatically calculate delivery costs by location" | No automatic calculation in this repo; `delivery_fee` is typed by hand. `utils/vehicle.js` does now define `FREE_DELIVERY_AREAS`, which is the nearest thing. Verify what the customer app does before claiming this. |

### C5 · The logical schema (Table 4.2.3.3.1) no longer describes the system
**Fix the document.** This is the largest single gap and the most mechanical to close.

**Tables in use but undocumented:** `booking_equipment` (30 uses — the entire
equipment spine), `category`, `package_category`. Plus `menu_selections` as a
column on `booking`.

**Columns in use but undocumented:** on `booking` — `booking_number`,
`booking_type`, `total_amount`, `delivery_fee`, `menu_selections`, `notes`,
`pricing_type`, `status_order`, `is_read`, `max_pax`, `extra_pax_price`; on
`payment` — **`booking_id`** (the document links PAYMENT to `package_id`, which
the code never uses); on `manager` — `active_session_id`,
`active_session_started_at` (a whole single-session-lock feature, undocumented);
on `equipment` — `damaged_quantity`, `maintenance_quantity`, `equipment_type`,
`pax_per_unit`.

**Documented but never used:** `PAYMENT.pay_installment`, `PAYMENT.package_id`,
`MENU_ITEM.menu_category`, `PACKAGE_MENU.package_menu_item_id`,
`PACKAGE_EQUIPMENT.inclusion_id`, `BOOKING.book_status` (the real column is
`booking_status`), `VEHICLE_ASSIGN.manager_id`, and the three conceptual-ERD
columns `assignment_date`, `expected_return_datetime`, `dispatch_notes`.

Also undocumented and load-bearing: **`booking.status_order` is not maintained by
the database.** Every status write must set it by hand or the row sorts into the
wrong group.

## 4. Checked and found sound

Worth stating, so the remediation doesn't churn code that is already right.

- **`status_order` pairing holds everywhere.** All nine writes that set
  `booking_status` set the matching `STATUS_ORDER`. The self-heal path is wired
  at both ends and ref-guarded against looping.
- **No circular imports.** Layering (`pages → hooks → utils → supabase`) is
  respected throughout.
- **No hooks called conditionally**, no components defined inside components, no
  missing `key` on any list, no `TODO`/`FIXME` markers, no empty catch blocks
  standing where logic belongs.
- **`useRealtimeRefresh`** is correct on every axis — ref-stabilised callback,
  serialised deps, cleanup that clears both the timer and the channel.
- **The password re-verification flow** (isolated client, `scope:'local'`
  sign-out, credential-rejection vs check-failure distinction) has no bypass.
- **The stored-value-vs-display-label trap** that bit this repo once has not
  returned — both Equipment and Vehicles map filter chips through
  `getAssignmentStatus` keys correctly.
- **Cancellation and rejection cleanup** correctly preserves history and leaves
  no active hold dangling.
- **Equipment's assign and delete guards** run in the right order and re-validate
  against the database rather than local state.
- **The 1000-row cap** is handled on every page except `Vehicles.jsx`, which is
  already logged as D9 in `blueprint-03-dispatch.md`.
- Undocumented but genuinely good, and worth claiming credit for in the defense:
  single-active-session enforcement with heartbeat and realtime kick, 30-minute
  inactivity logout, and password re-verification before destructive deletes.

## 5. Suggested order

1. **D2** — the ₱123,000 pricing error. One `pricing_type` branch.
2. **D1** — point both list pages at `useCompletionHandlers`. Corrupting payment
   data now, and the panel could trigger it live.
3. **D3** — the timezone shift. Four one-line fixes, same shape.
4. **C5 + C2's schema table** — the largest grading risk, and purely clerical.
   §3 of this document transcribes straight into a revision.
5. **C3** — populate `vehicle_assign.manager_id`. One line, closes an ethics
   commitment.
6. **D4, D5, D6** — real but narrower.
7. **C1, C4** — document rewording, no code change.

The pattern behind D1, D4 and D6 is worth naming: **logic that exists correctly
in a util or hook, re-typed into a page, then fixed on only one side.** Seven
files hold 60% of this codebase, and every drift defect in this report lives in
one of them.
